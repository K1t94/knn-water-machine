Реализовать регистрацию и авторизацию пользователя по номеру телефона через Orange SMS Senegal API с подтверждением OTP, принятием актуальных legal-документов и сохранением пользовательской сессии.

Используй общее ТЗ из docs/requirements.md.

Учитывай существующую структуру проекта, стек и архитектурные ограничения, зафиксированные в AGENTS.md и specs/001-project-bootstrap. Не создавай новый проект, не меняй базовую структуру репозитория и не дублируй задачи bootstrap.

Если требования текущей фичи противоречат общему ТЗ или ранее принятым архитектурным решениям, явно перечисли противоречия как вопросы для уточнения.

На момент разработки production-доступ к Orange SMS Senegal API может отсутствовать.

Реализовать FakeSmsProvider для development и автоматических тестов. Выбор провайдера производится через SMS_PROVIDER=fake|orange.

FakeSmsProvider может возвращать OTP только в локальном development-окружении. В staging и production запуск приложения с FakeSmsProvider должен быть запрещён.

Реальный OrangeSmsProvider реализовать по официальному контракту API. Фактическую проверку OAuth, Sender ID, Delivery Receipt и доставки SMS вынести в отдельный интеграционный этап после получения реквизитов заказчика.

Цель фичи:
- пользователь вводит сенегальский номер телефона;
- NestJS генерирует одноразовый код и отправляет его через Orange SMS Senegal API;
- пользователь подтверждает номер полученным кодом;
- при первой регистрации пользователь принимает актуальные legal-документы;
- после завершения регистрации приложение сохраняет сессию;
- повторный ввод OTP не требуется при каждом запуске приложения;
- пользователь считается зарегистрированным только после успешной проверки OTP и принятия всех обязательных legal-документов.

Важно:
Orange SMS Senegal API используется только для доставки SMS. Генерация и проверка OTP, защита от злоупотреблений, создание пользователя, legal acceptance и управление сессиями реализуются на NestJS-бэкенде.

## 1. Ввод номера телефона

- Основной и единственный регион MVP — Сенегал.
- Использовать международный код страны `+221`.
- Принимать номер в пользовательском формате, но перед отправкой на бэкенд нормализовать его в формат E.164.
- Проверять формат и допустимую длину номера.
- Не разрешать отправку OTP на неподдерживаемые страны.
- Не определять оператора только по префиксу номера, так как номер может быть перенесён между операторами.
- Показывать понятную ошибку при некорректном номере.

## 2. Отправка OTP

Для отправки SMS использовать Orange SMS Senegal API.

Сценарий:
1. Мобильное приложение отправляет номер телефона на NestJS.
2. NestJS проверяет номер и ограничения частоты запросов.
3. NestJS генерирует криптографически стойкий шестизначный цифровой OTP.
4. Бэкенд сохраняет только защищённое представление кода в Redis.
5. Бэкенд отправляет SMS через Orange SMS Senegal API.
6. Приложение открывает экран ввода OTP и запускает таймер повторной отправки.

Требования к OTP:
- код состоит из 6 цифр;
- срок действия — 5 минут;
- код одноразовый;
- после успешной проверки код немедленно становится недействительным;
- новый OTP аннулирует предыдущий активный код для этого номера;
- OTP нельзя хранить в PostgreSQL, Redis или логах в открытом виде;
- для хранения использовать HMAC или другой безопасный способ проверки кода;
- не возвращать OTP в API-ответах;
- исключение допускается только для изолированного тестового окружения и специально настроенных тестовых номеров.

Пример SMS:

`KAYNANN code: 123456. Valid for 5 minutes.`

Текст production-SMS должен:
- помещаться в одно SMS;
- использовать GSM-7 символы;
- не содержать кириллицу, emoji и лишние специальные символы;
- содержать название KAYNANN;
- указывать срок действия кода;
- не содержать кликабельные ссылки.

## 3. Интеграция с Orange SMS Senegal API

NestJS должен:
- получать OAuth access token Orange по `clientId` и `clientSecret`;
- кэшировать Orange access token до окончания срока его действия;
- отправлять SMS через официальный Orange SMS Senegal API;
- использовать согласованный Sender ID или sender address;
- сохранять технический идентификатор отправки, если Orange его возвращает;
- поддерживать получение Delivery Receipt, если эта возможность активирована;
- обрабатывать ошибки авторизации, недостаточный SMS-баланс, rate limit, timeout и временную недоступность Orange;
- выполнять ограниченные повторные попытки только для временных технических ошибок;
- не повторять запрос при явной ошибке номера или отклонении сообщения;
- не допускать бесконечных повторных отправок.

Секреты Orange:
- не должны попадать в React Native-приложение;
- не должны храниться в исходном коде;
- не должны попадать в публичный репозиторий или логи;
- должны передаваться через переменные окружения или используемое в проекте хранилище секретов.

Предусмотреть конфигурацию:
- `ORANGE_SMS_CLIENT_ID`;
- `ORANGE_SMS_CLIENT_SECRET`;
- `ORANGE_SMS_SENDER_ADDRESS`;
- `ORANGE_SMS_SENDER_NAME`;
- `ORANGE_SMS_API_URL`;
- параметры webhook для Delivery Receipt, если он используется.

Названия переменных можно адаптировать к принятому в проекте формату.

## 4. Абстракция SMS-провайдера

Интеграция с Orange не должна быть напрямую связана с бизнес-логикой авторизации.

Предусмотреть абстракцию SMS-провайдера, например:

- `SmsProvider`;
- `OrangeSmsProvider`;
- `SmsModule`.

Абстракция должна позволять в будущем добавить резервного провайдера без изменения OTP-сервиса и сценария регистрации.

Минимальная ответственность провайдера:
- отправить SMS;
- вернуть идентификатор сообщения, если он доступен;
- нормализовать ответ провайдера;
- преобразовать ошибки Orange во внутренние типизированные ошибки приложения.

Автоматическое переключение на резервного провайдера в рамках этой фичи не реализовывать.

## 5. Заменяемость SMS-провайдера

Бизнес-логика OTP не должна импортировать или вызывать OrangeSmsProvider напрямую.

OtpService должен зависеть только от абстракции SmsProvider через dependency injection.

Все реализации SMS-провайдеров должны использовать единый контракт:

- отправка сообщения;
- нормализованный результат отправки;
- единые категории ошибок;
- идентификатор сообщения;
- получение или обработка статуса доставки, если поддерживается провайдером.

Специфические DTO, HTTP-клиенты, OAuth-токены, URL, коды ошибок и модели Orange не должны выходить за пределы OrangeSmsProvider.

Выбор активного провайдера должен выполняться через конфигурацию:

SMS_PROVIDER=fake|orange

Добавление нового провайдера, например D7SmsProvider, не должно требовать изменений в:

- OtpService;
- AuthService;
- контроллерах авторизации;
- React Native-приложении;
- правилах регистрации;
- хранении OTP;
- управлении пользовательскими сессиями.

FakeSmsProvider разрешён только в development и test. Запуск production или staging с SMS_PROVIDER=fake должен завершаться ошибкой конфигурации.

OrangeSmsProvider должен быть покрыт контрактными тестами с замоканным HTTP API. Общий набор контрактных тестов должен применяться ко всем реализациям SmsProvider.

## 6. Повторная отправка OTP

- Разрешать повторную отправку через 60 секунд.
- Показывать оставшееся время до повторной отправки.
- Блокировать кнопку во время запроса.
- Не разрешать несколько параллельных запросов для одного номера.
- Новый код должен аннулировать предыдущий.
- Серверные ограничения должны работать независимо от ограничений интерфейса.

Предусмотреть лимиты:
- на номер телефона;
- на IP-адрес;
- на устройство или installation ID, если он используется в проекте;
- на общее количество отправленных SMS за определённый период;
- на дневной бюджет SMS.

Точные значения дополнительных лимитов определить на этапе планирования, но они должны быть конфигурируемыми.

## 7. Проверка OTP

Мобильное приложение отправляет номер телефона и введённый OTP на NestJS.

NestJS должен:
- найти актуальный OTP challenge;
- проверить срок действия;
- проверить количество оставшихся попыток;
- безопасно сравнить введённый код с сохранённым значением;
- после успешной проверки атомарно отметить код использованным;
- не позволять повторно использовать подтверждённый код;
- не допускать одновременную успешную проверку одного OTP несколькими запросами.

Разрешить не более 5 попыток ввода одного кода.

После превышения лимита:
- аннулировать OTP;
- потребовать запросить новый код;
- применить временное ограничение, если было несколько последовательных неудачных попыток.

## 8. Первый вход и legal-документы

После успешного OTP бэкенд определяет:

- существует ли зарегистрированный пользователь с этим номером;
- приняты ли им актуальные обязательные legal-документы.

Если пользователь новый:
- выдать короткоживущий registration token;
- получить с бэкенда актуальные legal-документы;
- показать экран принятия документов;
- завершить регистрацию только после их принятия.

Если пользователь существует, но появились новые обязательные версии документов:
- не пускать его на главный экран;
- запросить принятие новых версий;
- после принятия продолжить авторизацию.

Если пользователь существует и все актуальные документы приняты:
- завершить авторизацию;
- создать пользовательскую сессию;
- открыть главный экран.

## 9. Создание пользователя

Успешная отправка SMS или подтверждение OTP сами по себе не означают завершённую регистрацию.

Требования:
- доменная запись `User` создаётся или активируется только после успешного OTP и принятия обязательных legal-документов;
- завершение регистрации должно быть атомарным;
- операция должна быть идемпотентной;
- повторный запрос не должен создавать дубликаты пользователя или принятия документов;
- номер телефона хранится в нормализованном формате E.164;
- номер телефона должен быть уникальным среди активных пользователей;
- временные OTP challenge не являются пользователями системы;
- если registration token истёк, пользователь должен снова подтвердить номер через OTP.

При завершении регистрации сохранить:
- пользователя;
- нормализованный номер телефона;
- дату подтверждения номера;
- версии принятых документов;
- дату и время каждого принятия;
- технические данные аудита, предусмотренные проектом.

## 10. Пользовательская сессия

После регистрации или входа NestJS выдаёт:
- короткоживущий access token;
- долгоживущий refresh token.

Рекомендуемые значения:
- access token — 15 минут;
- refresh token — 60 дней.

Требования:
- React Native-приложение безопасно хранит refresh token;
- access token обновляется автоматически;
- повторный OTP не требуется, пока refresh-сессия действительна;
- использовать rotation refresh token;
- сервер должен уметь отзывать отдельную сессию;
- при повторном использовании старого refresh token связанная сессия должна быть отозвана;
- пользователь может иметь несколько сессий на разных устройствах;
- после явного выхода текущая сессия отзывается;
- при недействительной или истёкшей refresh-сессии требуется повторная OTP-авторизация;
- не хранить refresh token в базе в открытом виде.

## 11. Экраны и состояния

### Экран ввода телефона

Состояния:
- начальное;
- некорректный номер;
- отправка;
- OTP отправлен;
- временная ошибка Orange;
- превышен лимит запросов;
- отсутствует интернет;
- сервис временно недоступен.

### Экран ввода OTP

Состояния:
- ожидание ввода;
- проверка кода;
- неверный код;
- истёкший код;
- превышено количество попыток;
- таймер повторной отправки;
- повторная отправка;
- новый код отправлен;
- ошибка повторной отправки;
- успешное подтверждение.

Поддержать автоматическую подстановку OTP средствами операционной системы, если она доступна.

### Экран legal-документов

Состояния:
- загрузка документов;
- документы загружены;
- не все обязательные документы приняты;
- отправка согласия;
- документы изменились во время регистрации;
- ошибка завершения регистрации;
- успешное завершение.

## 12. Обработка ошибок и восстановление

Обработать как минимум:
- некорректный номер;
- неподдерживаемую страну;
- отсутствие сети;
- ошибку отправки SMS;
- недоступность Orange;
- ошибку получения Orange access token;
- недостаточный SMS-баланс;
- неправильную конфигурацию Sender ID;
- rate limit Orange;
- серверный rate limit;
- неверный OTP;
- истёкший OTP;
- использованный OTP;
- превышение количества попыток;
- отсутствие или истечение registration token;
- ошибку загрузки legal-документов;
- изменение актуальной версии legal-документов;
- повторное завершение регистрации;
- существующего пользователя;
- недоступность PostgreSQL или Redis;
- ошибку создания пользовательской сессии.

Если OTP успешно подтверждён, но бэкенд временно не смог завершить регистрацию, пользователь должен иметь возможность повторить завершение регистрации без нового SMS, пока registration token действителен.

Не показывать пользователю внутренние сообщения Orange, Redis, PostgreSQL или NestJS. Все ошибки должны преобразовываться в понятные продуктовые сообщения.

## 13. Безопасность

- Генерировать OTP через криптографически безопасный генератор.
- Не использовать `Math.random()`.
- Не хранить и не логировать OTP в открытом виде.
- Не логировать access token, refresh token, registration token и секреты Orange.
- Маскировать номер телефона в технических логах.
- Защитить endpoint’ы rate limiting.
- Предусмотреть защиту от SMS pumping.
- Ограничить расходы на отправку SMS.
- Использовать HTTPS.
- Использовать одноразовые OTP challenge.
- Защитить проверку OTP от race condition.
- Использовать безопасное сравнение кодов.
- Все ограничения должны выполняться на сервере.
- Development-, staging- и production-конфигурации должны быть разделены.

## 14. Наблюдаемость

Добавить технические метрики:
- количество запросов OTP;
- количество успешно отправленных SMS;
- количество ошибок отправки;
- количество подтверждённых OTP;
- количество неверных и истёкших кодов;
- среднее время доставки, если доступны Delivery Receipt;
- статистику ошибок по оператору, если оператор определяется по результатам доставки;
- текущий уровень расхода SMS;
- количество срабатываний rate limit.

Не включать в метрики и логи открытые OTP, токены и полные номера телефонов.

## 15. Основной пользовательский сценарий

1. Пользователь вводит сенегальский номер телефона.
2. NestJS создаёт OTP challenge.
3. Orange SMS Senegal API отправляет код.
4. Пользователь вводит полученный OTP.
5. NestJS подтверждает код и помечает его использованным.
6. Бэкенд проверяет существование пользователя и актуальность legal acceptance.
7. Новый пользователь принимает обязательные legal-документы.
8. NestJS атомарно создаёт пользователя и сохраняет принятие документов.
9. Бэкенд создаёт сессию и возвращает access и refresh tokens.
10. Приложение открывает главный экран.
11. При следующих запусках сессия восстанавливается без отправки нового OTP.

## 16. Сущности

Добавить в спецификацию необходимые сущности и их ответственность:

- `User`;
- `OtpChallenge`;
- `UserSession`;
- `LegalDocument`;
- `LegalAcceptance`;
- `SmsMessage` или `SmsDelivery`, если требуется хранить технический статус отправки.

Не фиксировать окончательную структуру таблиц до этапа планирования, но описать необходимые данные, связи, ограничения уникальности и жизненный цикл сущностей.

## 17. Критерии успешности

Добавь измеримые критерии:
- пользователь может зарегистрироваться по номеру `+221`;
- OTP нельзя использовать повторно;
- истёкший OTP не принимается;
- после пяти неверных попыток код блокируется;
- повторная отправка недоступна до окончания таймера;
- повторный запрос завершения регистрации не создаёт дубликаты;
- без принятия legal-документов нельзя открыть основное приложение;
- после перезапуска приложения действующая сессия восстанавливается без OTP;
- секреты Orange отсутствуют в мобильном приложении и репозитории;
- смена SMS-провайдера не требует изменения бизнес-логики OTP;
- ошибки Orange не раскрываются пользователю в исходном виде.

## 18. Вне рамок фичи

Не включай:
- покупку и выдачу воды;
- QR-сканер;
- взаимодействие с автоматами;
- MQTT;
- Wave и Orange Money;
- баланс литров;
- реферальную программу;
- push-уведомления;
- автоматическое переключение на резервного SMS-провайдера;
- поддержку телефонных номеров других стран;
- восстановление аккаунта через email;
- вход через Google, Apple или социальные сети.

На основе требований подготовь:
- пользовательские истории;
- приоритеты пользовательских историй;
- функциональные требования;
- критерии приёмки в формате Given/When/Then;
- состояния экранов;
- граничные случаи;
- бизнес-правила OTP;
- требования к регистрации и авторизации;
- требования к сессиям;
- требования к legal acceptance;
- требования к интеграции с Orange;
- измеримые критерии успешности.
