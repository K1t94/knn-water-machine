Сформируй tasks.md для реализации текущей Phone OTP Authentication feature на основе spec.md, plan.md, research.md, data-model.md и API-контрактов.

Учитывай существующую структуру monorepo и решения из specs/001-project-bootstrap. Не добавляй повторно задачи bootstrap.

Разбей задачи на небольшие проверяемые шаги и укажи точные пути создаваемых или изменяемых файлов.

Организуй задачи по этапам и пользовательским историям:

1. Общие контракты, конфигурация и модели данных.
2. OTP challenge и атомарная логика Redis.
3. Абстракция SmsProvider и shared contract tests.
4. FakeSmsProvider для development и test.
5. OrangeSmsProvider с замоканным Orange API.
6. Регистрация и принятие legal-документов.
7. Access/refresh sessions, rotation и replay detection.
8. API-контракты и NestJS endpoints.
9. React Native: телефон, OTP, legal и восстановление сессии.
10. Наблюдаемость, rate limits и защита от SMS pumping.
11. Интеграционные, security и acceptance-тесты.
12. Отдельный post-credential этап проверки реального Orange API.

Требования к задачам:

- каждая задача должна иметь однозначный проверяемый результат;
- указывать зависимости между задачами;
- помечать задачи, которые можно выполнять параллельно, маркером [P];
- сохранять привязку задач к User Story маркерами [US1], [US2], [US3], [US4];
- тесты добавлять вместе с соответствующей функциональностью, а не одним общим этапом в конце;
- сначала создавать контракты и модели, затем реализации;
- миграции PostgreSQL должны выполняться до зависимой от них бизнес-логики;
- Redis concurrency и atomicity должны иметь отдельные тестовые задачи;
- OrangeSmsProvider должен тестироваться без живых credentials через mock HTTP server;
- shared contract tests должны применяться к FakeSmsProvider и OrangeSmsProvider;
- staging и production должны иметь тест, запрещающий SMS_PROVIDER=fake;
- регистрация должна иметь тесты атомарности и идемпотентности;
- refresh rotation должна иметь concurrency- и replay-тесты;
- мобильные задачи должны учитывать все состояния экранов из spec.md;
- задачи по pending promo code должны только переносить его в контексте регистрации, без проверки и реферальных эффектов;
- post-credential Orange acceptance не должен блокировать локальную реализацию и автоматические тесты.

Для каждой пользовательской истории добавь независимый checkpoint, после которого её можно проверить отдельно.

Не включай:
- реферальные связи и бонусы;
- fallback SMS-провайдера;
- другие страны;
- покупку воды;
- QR;
- MQTT;
- платежи;
- баланс литров;
- push-уведомления.

После формирования tasks.md проверь, что каждый FR из spec.md покрыт хотя бы одной задачей. Если какое-либо требование невозможно сопоставить с задачей, перечисли его отдельно, не придумывая реализацию.
