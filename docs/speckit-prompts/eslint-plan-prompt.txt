Создай технический план реализации ESLint-конфигурации на основе текущего spec.md.

Перед планированием изучи:

- AGENTS.md;
- .specify/memory/constitution.md;
- текущий spec.md этой feature;
- корневой package.json и pnpm-workspace.yaml;
- package.json приложений apps/mobile и apps/api;
- существующие ESLint, TypeScript, Prettier и test-конфигурации;
- pnpm-lock.yaml для определения фактически установленных версий;
- spec.md, plan.md и релевантный код выполненной задачи
  specs/002-phone-otp-auth.

Задача 002-phone-otp-auth является основным примером текущей архитектуры,
стиля кода, использования React Native, Expo, MobX, RxJS и NestJS.
Не изменяй её продуктовое поведение.

Во время планирования:

1. Определи фактические версии ESLint, Expo, React Native, React,
 TypeScript, NestJS, Vitest, Prettier и связанных инструментов.

2. Сохрани существующий ESLint 9 Flat Config. Не выполняй миграцию
   формата конфигурации, если она не требуется.

3. Спроектируй:
   - общий TypeScript baseline;
   - отдельную конфигурацию для apps/mobile;
   - отдельную конфигурацию для apps/api;
   - overrides для тестов, mocks, fixtures, scripts, migrations,
     seeds и конфигурационных файлов;
   - единый централизованный список исключений.

4. Для mobile сначала оцени eslint-config-expo/flat как базовую
   конфигурацию. Проверь, какие React, React Hooks, React Native
   и другие правила она уже включает, чтобы не устанавливать
   и не включать дублирующие плагины.

5. Оцени только реально необходимые кандидаты:

   - eslint-config-expo;
   - typescript-eslint;
   - eslint-plugin-react;
   - eslint-plugin-react-hooks;
   - eslint-plugin-react-native;
   - eslint-plugin-react-native-a11y;
   - eslint-plugin-import либо eslint-plugin-import-x;
   - eslint-plugin-unused-imports;
   - eslint-plugin-testing-library;
   - плагин для фактически используемого test runner;
   - eslint-config-prettier;
   - поддерживаемый инструмент для RxJS только при наличии надёжной
     совместимости с ESLint 9 Flat Config.

6. Не считай список кандидатов обязательным набором зависимостей.
   Для каждого кандидата зафиксируй:

   - выбран или отклонён;
   - какую проверку он добавляет;
   - совместимость с установленными версиями;
   - поддержку Flat Config;
   - активность поддержки;
   - пересечение с eslint-config-expo и другими плагинами;
   - риск false positives;
   - влияние на скорость lint;
   - альтернативу для отклонённого модуля, если соответствующее
     требование остаётся обязательным.

7. Выбери только один механизм анализа импортов:
   eslint-plugin-import или eslint-plugin-import-x.
   Учти TypeScript aliases и файлы *.ios.* и *.android.*.

8. Отдельно определи, какие архитектурные ограничения можно надёжно
   проверить ESLint-правилами, а какие должны остаться предметом
   code review. Не предлагай эвристические правила с большим
   количеством ложных срабатываний.

9. Для type-aware правил определи:
   - какие tsconfig используются;
   - какие файлы имеют полноценную type information;
   - как будут проверяться конфигурационные файлы вне основных tsconfig;
   - как избежать существенного замедления lint.

10. Не включай строгий глобальный запрет inline styles.
    Не включай правила, требующие браузерные DOM-атрибуты
    от React Native-компонентов.

11. Предложи способ проверки правил на контролируемых ошибочных примерах.
    Эти примеры не должны попадать в production-сборку или обычный
    анализ исходного кода.

12. Запланируй измерение времени:
    - общей lint-команды;
    - mobile lint;
    - API lint;
    - type-aware частей конфигурации.

13. Раздели исправления существующего кода на:
    - полностью безопасные автоматические исправления;
    - механические ручные исправления;
    - потенциально меняющие поведение исправления, которые нельзя
      выполнять в рамках этой feature.

14. Не изменяй OTP, legal, регистрацию, сессии, SMS, навигацию,
    публичные API-контракты, базы данных или другое продуктовое поведение.

В плане явно перечисли:

- итоговую структуру ESLint-конфигурации;
- изменяемые и создаваемые файлы;
- выбранные и отклонённые зависимости;
- команды lint и lint:fix;
- способ проверки обязательных категорий ошибок;
- порядок внедрения правил;
- стратегию исправления существующего кода;
- способ проверки отсутствия конфликтов с Prettier;
- риски, ограничения и отложенные проверки.

Не устанавливай зависимости и не изменяй код на этапе планирования.
