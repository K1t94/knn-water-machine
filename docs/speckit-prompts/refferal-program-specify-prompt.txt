  - существующие session, registration, legal и wallet-контракты.

  ## Цель

  Реализовать простую и надёжную реферальную программу, которая связывает
  пригласившего пользователя с приглашённым и начисляет бонусы через существующий
  wallet/ledger-домен.

  Feature должна завершить уже начатый в задаче 002 сценарий промокода и
  использовать внутренние идемпотентные команды задачи 004 для начисления литров.

  В рамках feature необходимо реализовать:

  - уникальный промокод каждого зарегистрированного пользователя;
  - реферальный deep link с этим промокодом;
  - создание неизменяемой реферальной связи;
  - применение промокода во время регистрации;
  - применение промокода зарегистрированным пользователем до первой успешной
    покупки воды;
  - однократное начисление welcome-бонуса приглашённому;
  - однократное начисление referral-бонуса пригласившему;
  - получение пользователем своего промокода и referral link;
  - получение истории приглашений и суммарного начисленного объёма;
  - минимальный мобильный интерфейс реферальной программы.

  Не реализовывать платежи, покупку воды, QR, автоматы, MQTT, dispensing,
  административное управление бонусами или многоуровневую реферальную систему.

  ## Временные размеры бонусов

  До получения окончательных бизнес-значений используй следующие настраиваемые
  значения для разработки и тестирования:

  - welcome-бонус приглашённому: 10 литров, то есть 10 000 миллилитров;
  - referral-бонус пригласившему: 5 литров, то есть 5 000 миллилитров.

  Приглашённый пользователь не получает отдельный referral-бонус сверх
  welcome-бонуса.

  Размеры бонусов должны:

  - храниться и обрабатываться backend в целых миллилитрах;
  - задаваться backend-конфигурацией;
  - не быть зашиты в mobile-код;
  - безопасно изменяться без обновления мобильного приложения;
  - фиксироваться в ledger в размере, действовавшем в момент начисления;
  - иметь development/test defaults;
  - требовать явной production-конфигурации, если это соответствует принятому
    подходу проекта.

  Не принимать эти временные значения как окончательное продуктовое решение.

  ## Бизнес-правила

  Зафиксируй следующие правила:

  - у каждого зарегистрированного пользователя ровно один стабильный уникальный
    промокод;
  - пользователь не может применить собственный промокод;
  - промокод можно применить не более одного раза;
  - после успешного применения код нельзя заменить или удалить;
  - повторный запрос с тем же кодом должен быть идемпотентным;
  - повторный запрос с другим кодом после закрепления должен завершаться
    стабильной конфликтной ошибкой;
  - несуществующий или недоступный код должен возвращать безопасную публичную
    ошибку без раскрытия данных владельца;
  - регистрирующийся пользователь может изменить или удалить pending promo code
    до завершения регистрации;
  - pending promo code не создаёт реферальную связь и не начисляет бонусы до
    завершения OTP и принятия актуальных legal-документов;
  - после завершения регистрации связь и бонусы создаются атомарно;
  - зарегистрированный пользователь может применить код отдельным явным
    действием только до первой успешно завершённой покупки воды;
  - неуспешная, отменённая или незавершённая покупка не должна блокировать
    применение промокода;
  - поскольку purchase-домен ещё не реализован, спецификация должна определить
    явный интеграционный контракт или eligibility lock для будущей feature, не
    реализуя саму покупку;
  - реферальная связь после создания неизменяема;
  - удаление или блокировка аккаунта не должна переносить связь к другому
    пригласившему;
  - бонус пригласившему начисляется только после завершения регистрации
    приглашённого либо после успешного применения кода уже зарегистрированным
    пользователем;
  - каждый положенный бонус начисляется ровно один раз;
  - ошибка начисления не должна оставлять частично созданную связь;
  - одновременные запросы не должны создавать несколько связей или начислений;
  - начисления выполняются только через внутренние wallet application-команды;
  - referral-домен не должен напрямую изменять wallet projection или ledger.

  Отдельно зафиксируй ожидаемое поведение welcome-бонуса для пользователя без
  промокода: согласно MVP он должен однократно получить welcome-бонус после
  завершения регистрации, независимо от наличия реферальной связи.

  ## Backend

  Спроектируй отдельный NestJS referral-модуль в соответствии с существующей
  архитектурой:

  - тонкие HTTP-контроллеры;
  - бизнес-правила в domain/application слоях;
  - Prisma только в infrastructure-слое;
  - явные request DTO и response models;
  - авторизация через существующую session-модель и AccessSessionGuard;
  - интеграция с registration/legal lifecycle без изменения существующих
    публичных auth-контрактов;
  - интеграция с wallet через внутренние application-команды;
  - отсутствие прямого доступа к wallet Prisma-моделям;
  - стабильные публичные ошибки;
  - транзакционная и конкурентно-безопасная работа с PostgreSQL;
  - идемпотентность на уровне базы данных, а не только application-кода.

  Определи минимальные публичные API-контракты для:

  - получения собственного промокода и referral link;
  - применения промокода зарегистрированным пользователем;
  - получения referral summary;
  - получения истории приглашений с детерминированной пагинацией.

  Не добавляй публичные endpoints для:

  - ручного начисления бонусов;
  - изменения размеров бонусов;
  - смены пригласившего;
  - произвольного создания или удаления реферальных связей;
  - прямого вызова wallet credit;
  - административного изменения referral-данных.

  ## Модель данных

  В спецификации зафиксируй требования к:

  - стабильному уникальному промокоду пользователя;
  - нормализации и сравнению промокодов;
  - владельцу промокода;
  - неизменяемой связи inviter/invitee;
  - времени создания и применения связи;
  - способу применения: registration или post-registration;
  - состоянию eligibility для применения после регистрации;
  - защите от self-referral;
  - уникальности invitee в реферальных связях;
  - защите от повторного начисления welcome-бонуса;
  - защите от повторного начисления inviter-бонуса;
  - business event/idempotency keys для wallet-команд;
  - связи referral-событий с wallet ledger без раскрытия внутренних ключей;
  - индексах, unique constraints и CHECK constraints;
  - детерминированной cursor pagination истории;
  - запрете изменения или удаления подтверждённой реферальной связи через
    application-код.

  Не выбирай окончательную Prisma-схему на этапе specification, если это относится
  к техническому плану. Зафиксируй инварианты и наблюдаемое поведение.

  ## Идемпотентность и атомарность

  Спецификация должна требовать:

  - ровно один welcome-бонус на пользователя;
  - ровно один inviter-бонус на реферальную связь;
  - стабильные business keys для wallet ledger;
  - безопасный повтор registration completion;
  - безопасный повтор apply promo;
  - защиту от конкурентного применения разных промокодов;
  - защиту от конкурентного применения одного промокода;
  - атомарность создания связи и фиксации намерения начислить бонус;
  - отсутствие состояния, при котором связь считается успешно созданной, но
    обязательное начисление навсегда потеряно;
  - явную стратегию восстановления после временной ошибки wallet-команды;
  - отсутствие распределённых транзакций, скрытых за ложной гарантией
    атомарности.

  Если referral и wallet невозможно надёжно изменить одной Prisma/PostgreSQL
  транзакцией из-за текущих архитектурных границ, зафиксируй это как технический
  вопрос для plan и потребуй надёжный transactional/outbox либо другой
  идемпотентный механизм восстановления.

  ## Public API и безопасность

  Публичные ответы не должны раскрывать:

  - внутренние database IDs других пользователей;
  - телефон пригласившего;
  - полный телефон приглашённого;
  - wallet business keys;
  - внутренние idempotency keys;
  - технические статусы фоновой обработки;
  - конфигурацию бонусов, кроме значений, необходимых для интерфейса.

  История приглашений может содержать только безопасное представление
  приглашённого пользователя, например маскированный телефон, публичный статус,
  дату и начисленный объём.

  Пользователь должен получать только собственный promo/referral summary и
  собственную историю приглашений.

  ## Mobile

  Предусмотри минимальную интеграцию с текущими MobX и RxJS-паттернами:

  - referral API client;
  - типы публичных ответов;
  - referral store;
  - disposable flow service;
  - cold Observable для сетевых операций;
  - загрузку собственного кода, referral link, summary и истории;
  - копирование и системный share referral link;
  - экран применения промокода зарегистрированным пользователем;
  - поддержку входящего referral deep link;
  - явное подтверждение применения кнопкой;
  - loading, empty, loaded, success и retryable error states;
  - deterministic pagination истории приглашений;
  - защиту от обновления состояния устаревшим запросом;
  - очистку referral-данных при logout, потере или замене сессии;
  - повторную загрузку после login и session restoration;
  - блокировку поля после успешного применения;
  - отображение причины недоступности применения после будущей первой успешной
    покупки.

  Не проектируй полный главный экран и не меняй навигацию шире необходимого.

  ## Тестирование

  Предусмотри unit, integration и PostgreSQL-backed тесты для:

  - генерации уникального промокода;
  - нормализации и поиска промокода;
  - запрета self-referral;
  - неизвестного промокода;
  - применения кода во время регистрации;
  - изменения и удаления pending кода до завершения регистрации;
  - отсутствия начислений до OTP и legal completion;
  - welcome-бонуса без промокода;
  - welcome-бонуса приглашённому;
  - отсутствия дополнительного referral-бонуса приглашённому;
  - inviter-бонуса пригласившему;
  - точных значений 10 000 и 5 000 миллилитров в test configuration;
  - повторного registration completion;
  - повторного применения того же кода;
  - конфликтующего применения другого кода;
  - конкурентного применения одного кода;
  - конкурентного применения разных кодов;
  - атомарного rollback;
  - восстановления после временной ошибки начисления;
  - глобальной database-backed идемпотентности;
  - неизменяемости подтверждённой связи;
  - изоляции данных пользователей;
  - безопасного маскирования истории;
  - детерминированной cursor pagination;
  - применения до eligibility lock;
  - отказа после eligibility lock;

  - очистки состояния при logout/session replacement;

  идемпотентность должны проверяться на настоящем PostgreSQL, а не только mocks
  или SQLite.

  ## Миграция существующих пользователей

  Явно зафиксируй как вопрос или выбранное безопасное поведение:

  - как создаются промокоды пользователям, существовавшим до feature 005;
  - должен ли существующим пользователям начисляться welcome-бонус задним числом;
  - как избежать массового неожиданного начисления при миграции;
  - выполняется ли backfill промокодов миграцией, отдельной идемпотентной командой
    или лениво.

  По умолчанию не начисляй существующим пользователям бонусы задним числом без
  отдельного подтверждения. Промокоды существующим пользователям должны быть
  созданы безопасно и детерминированно либо через явно описанный backfill.

  ## Ограничения

  - Не изменять OTP, legal, SMS и session API-контракты.
  - Не менять продуктовое поведение завершённых задач без явной необходимости.
  - Не реализовывать покупку или первую успешную выдачу воды.
  - Не реализовывать платежи Wave или Orange Money.
  - Не реализовывать QR, карту, автоматы, MQTT или dispensing.
  - Не реализовывать source buckets и bonus-first списание.
  - Не добавлять многоуровневые referrals.
  - Не начислять бонус за приглашённых приглашённого пользователя.
  - Не добавлять срок действия бонусных литров.
  - Не добавлять вывод или денежную конвертацию бонусов.
  - Не добавлять административное редактирование referral-связей.
  - Не использовать floating-point значения для литров.
  - Не использовать автоматическую синхронизацию Prisma schema.
  - Не добавлять тяжёлые зависимости без подтверждённой необходимости.
  - Использовать текущий package manager, ESLint, TypeScript, Prettier и test
    runner проекта.

  ## Критерии приёмки

  1. Каждый зарегистрированный пользователь имеет один стабильный уникальный
     промокод.
  2. Пользователь может получить свой код и referral link.
  3. Pending промокод не создаёт связь до завершения OTP и legal.
  4. После завершения регистрации пользователь ровно один раз получает
     welcome-бонус 10 000 мл в test configuration.
  5. Наличие промокода не добавляет приглашённому бонус сверх welcome-бонуса.
  6. Пригласивший ровно один раз получает 5 000 мл в test configuration.
  7. Все начисления проходят через существующий immutable wallet ledger.
  8. Повтор одного бизнес-события не создаёт новую связь или начисление.
  9. Self-referral, замена кода и повторное применение другого кода запрещены.
  10. Конкурентные запросы не создают дублирующие связи или бонусы.
  11. Зарегистрированный пользователь может явно применить код до eligibility
      lock и не может после него.
  12. Пользователь видит только собственные referral-данные и безопасно
      замаскированную историю.
  13. История имеет детерминированную cursor pagination.
  14. Ошибка не оставляет потерянное обязательное начисление или частично
      подтверждённый результат.
  15. Mobile корректно обрабатывает deep link, session lifecycle и сетевые
      состояния.
  16. Новая реализация проходит lint, format check, typecheck и тесты.
  17. Поведение задач 002-phone-otp-auth и 004-water-wallet-ledger сохраняется.
  18. Feature не добавляет публичных способов произвольно начислять литры.

  Если docs/mvp-requirements.md, существующая auth-модель, wallet API или Prisma
  schema противоречат этим требованиям, явно зафиксируй конфликт, допущение или
  открытый вопрос. Не скрывай невозможность общей транзакции между модулями и не
  принимай дополнительные продуктовые решения без подтверждения.
