Подготовь технический план реализации текущей спецификации Phone OTP Authentication.

Источники требований и ограничений:
- текущий spec.md этой фичи;
- docs/mvp-requirements.md версии 0.12 — общий источник требований MVP;
- AGENTS.md;
- constitution проекта;
- существующие решения и структура из specs/001-project-bootstrap.

Не используй docs/requirements.md: такого файла в проекте нет.

Перед проектированием изучи существующий репозиторий и повторно используй уже выбранные в bootstrap:
- структуру monorepo;
- React Native-приложение;
- NestJS API;
- PostgreSQL и ORM;
- Redis или существующий transient store;
- систему конфигурации;
- миграции;
- валидацию;
- логирование;
- тестовую инфраструктуру;
- API-клиент мобильного приложения.

Не создавай новый проект, не переделывай bootstrap и не дублируй существующую инфраструктуру.

## Цель планирования

Спроектировать реализацию:

- OTP-регистрации и входа по сенегальскому номеру `+221`;
- отправки SMS через заменяемый `SmsProvider`;
- `FakeSmsProvider` для development и test;
- `OrangeSmsProvider` для Orange SMS Senegal API;
- принятия актуальных legal-документов;
- создания пользователя только после OTP и legal acceptance;
- access/refresh-сессий с ротацией refresh token;
- восстановления сессии в React Native;
- безопасного хранения временных OTP в Redis;
- поддержки pending promo code без его проверки и применения.

## Архитектурные ограничения

1. OTP-логика не должна зависеть напрямую от Orange.

2. `OtpService`, `AuthService`, контроллеры и React Native-приложение должны работать только с внутренними контрактами приложения.

3. Все особенности Orange должны оставаться внутри инфраструктурного адаптера:
   - OAuth client credentials;
   - HTTP endpoint;
   - sender address и Sender Name;
   - Orange DTO;
   - provider message ID;
   - коды ошибок;
   - retry;
   - Delivery Receipt.

4. Активный провайдер выбирается конфигурацией:

   `SMS_PROVIDER=fake|orange`

5. Добавление нового провайдера не должно требовать изменения:
   - OTP-логики;
   - регистрации;
   - сессий;
   - контроллеров;
   - мобильных экранов;
   - API-контрактов.

6. `FakeSmsProvider` разрешён только в development и test. Staging и production должны завершать запуск ошибкой, если выбран fake.

7. Production-реквизиты Orange сейчас могут отсутствовать. Фича должна полностью разрабатываться и тестироваться с fake-провайдером и замоканным Orange API.

8. Реальную проверку OAuth, Sender Name, баланса, доставки на сети Сенегала и Delivery Receipt выделить в отдельный post-credential acceptance stage.

## Требуемые результаты планирования

### 1. Архитектура NestJS

Определи границы и зависимости необходимых модулей. Как минимум рассмотри:

- AuthModule;
- OtpModule;
- SmsModule;
- UsersModule;
- LegalModule;
- SessionsModule;
- OrangeSmsProvider;
- FakeSmsProvider.

Названия адаптируй к существующей структуре проекта.

Покажи направление зависимостей между:
- доменной логикой;
- application services;
- provider contracts;
- инфраструктурными адаптерами;
- PostgreSQL;
- Redis;
- внешним Orange API.

Не допускай импорта Orange-классов в OTP, Auth, Users, Legal и мобильное приложение.

### 2. Хранение данных

Распредели данные между PostgreSQL и Redis.

В PostgreSQL должны храниться долгоживущие сущности, включая:
- User;
- UserSession;
- LegalDocument;
- LegalAcceptance;
- минимальный SmsDelivery, если он действительно нужен;
- необходимые данные аудита.

В Redis должны храниться временные данные, включая:
- OtpChallenge;
- TTL OTP;
- количество попыток;
- resend cooldown;
- временные блокировки;
- registration authorization или его серверное состояние, если выбран stateful-подход;
- rate-limit counters;
- глобальные и дневные лимиты отправки.

Для каждой сущности определи:
- поля;
- индексы;
- уникальные ограничения;
- TTL или retention;
- состояния;
- переходы;
- правила удаления;
- защиту от конкурентных запросов.

Не хранить plaintext OTP, plaintext refresh token и полные секреты провайдера.

### 3. OTP challenge

Спроектируй атомарный жизненный цикл OTP:

- серверная нормализация номера в E.164;
- создание шестизначного кода через криптографический генератор;
- HMAC или другой безопасный способ хранения проверочного значения;
- срок действия 5 минут;
- максимум 5 неверных попыток;
- resend cooldown 60 секунд;
- один актуальный challenge на номер;
- аннулирование предыдущего challenge при выпуске нового;
- атомарное успешное использование;
- защита от двух одновременных успешных проверок;
- защита от параллельных send-запросов;
- поведение при ошибке SMS после подготовки challenge.

Выбери конкретный механизм атомарности Redis, совместимый с существующим стеком: транзакция, Lua script либо другой обоснованный способ.

### 4. Anti-abuse и SMS budget

Спецификация требует выбрать дополнительные конфигурируемые значения на этапе планирования.

Предложи безопасные, но не чрезмерные значения для MVP:
- число отправок на номер за час и сутки;
- число отправок на IP за час;
- число отправок на installation/device ID;
- временная блокировка после нескольких исчерпанных challenge;
- глобальный суточный лимит SMS;
- суточный денежный лимит;
- максимальное число параллельных запросов;
- длительность хранения rate-limit counters.

Все значения должны настраиваться через конфигурацию.

Опиши порядок проверки лимитов и способ предотвращения SMS pumping. Отказ по rate limit не должен раскрывать наличие пользователя.

### 5. Регистрация и legal acceptance

Спроектируй сценарии:

- новый пользователь;
- существующий пользователь с актуальными документами;
- существующий пользователь с устаревшими legal acceptance;
- изменение версии документа во время регистрации;
- временная ошибка после успешного OTP;
- повторный и параллельный запрос завершения регистрации.

Выбери срок действия registration authorization и способ её реализации.

Registration authorization:
- выдаётся только после OTP;
- разрешает только получение и принятие legal-документов и завершение регистрации;
- не даёт доступ к основному приложению;
- не является полноценной пользовательской сессией;
- должна быть отзываемой или одноразовой;
- после истечения требует новый OTP.

Завершение регистрации должно одной транзакцией создавать или активировать:
- User;
- phone confirmation;
- LegalAcceptance для точных актуальных версий;
- первоначальную UserSession.

Опиши механизм идемпотентности и защиты от дубликатов.

### 6. Pending promo code

Учти FR-023 и BR-010.

Промокод:
- может быть передан из deep link;
- может быть введён вручную;
- может быть изменён или удалён;
- переносится как pending registration context;
- не проверяется в этой фиче;
- не блокирует регистрацию;
- не создаёт реферальную связь;
- не начисляет бонусы.

Определи минимальный способ безопасно перенести промокод до завершения регистрации, чтобы не связывать OTP-фичу с будущим ReferralModule.

### 7. Пользовательские сессии

Спроектируй:
- access token сроком 15 минут;
- refresh token сроком 60 дней;
- безопасную генерацию refresh token;
- хранение только защищённого представления на сервере;
- refresh token rotation;
- rotation lineage;
- обнаружение повторного использования старого токена;
- атомарное обновление;
- отзыв сессии при replay;
- отдельные сессии устройств;
- выход только с текущего устройства;
- очистку просроченных и отозванных сессий.

Выбери формат access token и механизм подписи в соответствии с существующей архитектурой проекта.

Определи, какие данные входят в токены, а какие всегда загружаются с сервера.

Не помещай полный номер телефона, legal-документы или секретные данные в токены без необходимости.

### 8. React Native

Спроектируй мобильную часть:

- экран ввода номера;
- фиксированный контекст `+221`;
- ввод, редактирование и удаление pending promo code;
- экран OTP;
- 60-секундный resend timer;
- OTP autofill средствами ОС;
- экран legal acceptance;
- маршрутизацию нового и существующего пользователя;
- восстановление сессии при запуске;
- автоматическое обновление access token;
- безопасное хранение refresh token;
- очистку авторизации при недействительной сессии;
- блокировку повторных нажатий;
- сохранение безопасного состояния при отсутствии сети.

Для secure storage используй уже доступное и совместимое с текущей React Native/Expo-конфигурацией решение. Если подходящего решения в bootstrap нет, сравни допустимые варианты в research.md и выбери один.

Не хранить OTP, refresh token или registration authorization в обычном AsyncStorage, если они требуют защищённого хранения.

### 9. API-контракты

Определи REST API и DTO как минимум для:

- запроса OTP;
- повторной отправки OTP;
- проверки OTP;
- получения актуальных legal-документов;
- завершения регистрации;
- принятия новых legal-версий существующим пользователем;
- обновления access token;
- выхода;
- Orange Delivery Receipt callback, если он включён конфигурацией.

Для каждого endpoint опиши:
- запрос;
- успешный ответ;
- безопасные коды ошибок;
- требования авторизации;
- идемпотентность;
- rate limits;
- поведение при повторных запросах.

Не возвращать клиенту внутренние Orange-ошибки, полные номера телефонов, OTP и provider payload.

Сформировать или обновить OpenAPI-контракт в соответствии с принятым в bootstrap процессом.

### 10. Orange SMS Senegal

В research.md проверь текущую официальную документацию Orange и зафиксируй:
- получение OAuth access token;
- срок действия и кэширование токена;
- endpoint отправки SMS;
- формат sender address;
- Sender Name;
- формат номера получателя;
- структуру запроса и ответа;
- provider message identifier;
- documented error responses;
- rate limits;
- возможности Delivery Receipt.

Для OAuth-токена:
- не запрашивать новый токен для каждого SMS;
- кэшировать до безопасного момента перед истечением;
- синхронизировать параллельное обновление токена.

Для отправки:
- retry только временных ошибок;
- ограниченный backoff;
- отсутствие retry для invalid recipient, rejected message, invalid credentials и invalid configuration;
- нормализация ошибок во внутренние стабильные категории.

Не придумывать недокументированные поля Orange. Не делать live-вызовы без явных production/test credentials.

### 11. Delivery Receipt

Delivery Receipt не влияет на успешность OTP-проверки и не подтверждает владение номером.

Определи:
- нужен ли SmsDelivery в первой локально тестируемой версии;
- минимальный webhook-контракт;
- проверку подлинности callback в пределах возможностей Orange;
- идемпотентность повторных событий;
- обработку поздних и неизвестных message ID;
- минимальный retention;
- feature flag для отключения до получения реквизитов.

Фактическую live-активацию оставить для post-credential acceptance stage.

### 12. Ошибки и наблюдаемость

Создай внутреннюю классификацию ошибок:
- invalid phone;
- unsupported country;
- local rate limit;
- SMS budget exhausted;
- invalid Orange configuration;
- Orange authentication failure;
- insufficient Orange balance;
- Orange rate limit;
- invalid recipient;
- rejected message;
- timeout;
- temporary provider failure;
- invalid, expired, used или exhausted OTP;
- invalid registration authorization;
- stale legal version;
- dependency failure;
- session creation failure;
- refresh failure.

Определи продуктовые коды ошибок для мобильного приложения.

Добавь безопасные метрики:
- OTP requested;
- SMS accepted;
- normalized send failure;
- OTP confirmed;
- incorrect/expired OTP;
- rate-limit activation;
- budget-limit activation;
- refresh success/failure;
- session replay detection;
- Delivery Receipt latency/status при наличии.

Не включать в логи, traces и метрики:
- plaintext OTP;
- полный номер;
- access/refresh/registration tokens;
- Orange credentials;
- полный provider payload.

### 13. Тестирование

Подготовь стратегию:

- unit-тесты OTP state machine;
- concurrency-тесты send и verify;
- тесты TTL, пяти попыток и cooldown;
- shared contract tests для SmsProvider;
- FakeSmsProvider tests;
- OrangeSmsProvider tests с mock HTTP server;
- тесты OAuth token cache и конкурентного refresh;
- тесты нормализации Orange-ошибок;
- integration-тесты NestJS + PostgreSQL + Redis;
- тесты транзакционности и идемпотентности регистрации;
- тесты stale legal versions;
- тесты refresh rotation и replay;
- тесты нескольких device sessions;
- тесты запрета fake в staging/production;
- мобильные тесты основных состояний;
- security-тесты на отсутствие секретов и чувствительных данных;
- отдельный manual acceptance checklist после получения Orange-реквизитов.

Тесты основной фичи должны выполняться без живого Orange-аккаунта.
