Создай спецификацию для настройки единых ESLint-правил в mobile- и api-репозиториях проекта.

Перед созданием спецификации изучи:

- AGENTS.md;
- .specify/memory/constitution.md;
- актуальную структуру репозитория;
- package.json и существующие ESLint/TypeScript-конфигурации frontend и backend;
- полностью выполненную задачу specs/002-phone-otp-auth;
- код, созданный в рамках 002-phone-otp-auth, как основной пример текущего стиля и архитектуры проекта.

Цель задачи:

Настроить понятные, строгие, но практически применимые ESLint-правила отдельно для frontend и backend. Правила должны выявлять реальные ошибки, поддерживать единый стиль кода и учитывать особенности используемых фреймворков.

Требования к общим правилам TypeScript:

- запрет неиспользуемых импортов, переменных и параметров с разумными исключениями;
- контроль необработанных Promise и Observable;
- запрет случайного игнорирования Promise и Observable;
- безопасная работа с async/await и Observable;
- выявление недостижимого и дублирующегося кода;
- контроль лишних приведений типов и небезопасного использования типов;
- ограничение использования any без необоснованного полного запрета;
- единообразный порядок импортов;
- отсутствие циклических зависимостей, если это возможно проверять без заметного замедления lint;
- запрет console в production-коде с допустимыми исключениями для инфраструктурных файлов;
- понятные правила именования;
- корректная работа с type-only imports;
- исключение сгенерированных файлов, build-каталогов, зависимостей, coverage и временных файлов.

Требования к ESLint для frontend:

Frontend является React Native-приложением. Перед выбором конфигурации и
плагинов изучи:

- фактическую версию React Native;
- используется ли Expo и какая установлена версия Expo SDK;
- версию React;
- версию TypeScript;
- версию ESLint;
- существующий формат ESLint-конфигурации;
- frontend-код, созданный в рамках задачи 002-phone-otp-auth.

Используй популярные и поддерживаемые ESLint-конфигурации и плагины,
подходящие для фактического frontend-стека.

Рассмотри следующие модули:

- eslint-config-expo — как базовую конфигурацию, если проект использует Expo;
- typescript-eslint — для TypeScript-правил, включая правила с информацией о типах, если их использование не делает lint неоправданно медленным;
- eslint-plugin-react — для правил React и JSX;
- eslint-plugin-react-hooks — для Rules of Hooks, exhaustive-deps и других
  актуальных проверок React Hooks;
- eslint-plugin-react-native — только после проверки совместимости с
  текущей версией ESLint и используемым форматом конфигурации;
- eslint-plugin-react-native-a11y — для базовых проверок доступности
  React Native-интерфейсов;
- eslint-plugin-import или eslint-plugin-import-x — для проверки импортов
  и архитектурных границ; выбрать один поддерживаемый вариант;
- eslint-plugin-unused-imports — если он совместим с выбранной версией
  TypeScript ESLint и не дублирует другие правила;
- eslint-plugin-testing-library — если frontend-тесты используют
  React Native Testing Library;
- соответствующий плагин тестового раннера — только если Jest, Vitest
  или другой test runner действительно используется в проекте;
- eslint-config-prettier — если проект использует Prettier, чтобы исключить
  конфликтующие правила форматирования.

Этот список является набором кандидатов, а не требованием установить каждый
модуль. В спецификации зафиксируй критерии выбора. Окончательный набор
зависимостей должен быть определён в плане после проверки:

- совместимости с установленными версиями;
- активности поддержки;
- наличия Flat Config support, если проект использует Flat Config;
- отсутствия дублирующих правил;
- отсутствия большого количества false positives;
- влияния на скорость lint;
- реальной пользы для текущего проекта.

Обязательные категории frontend-проверок:

1. React Hooks:
- запрет нарушения Rules of Hooks;
- проверка зависимостей useEffect, useMemo и useCallback;
- поддержка собственных effect hooks, если они существуют;
- выявление небезопасных обновлений состояния внутри эффектов.

2. React и JSX/TSX:
- корректное использование компонентов и props;
- отсутствие устаревшего требования импортировать React в каждый файл;
- корректное использование key в списках;
- запрет распространённых ошибок JSX;
- отсутствие правил, предназначенных исключительно для DOM, если они неприменимы к React Native.

3. React Native:
- проверка неиспользуемых StyleSheet-стилей;
- выявление некорректного JSX-текста вне компонента Text;
- контроль inline styles настроить с учётом практичности и существующей архитектуры, не включая строгий запрет автоматически;
- не применять web-only правила к React Native-компонентам;
- учитывать Platform.select и платформенные файлы *.ios.* и *.android.*.

4. Доступность:
- проверка accessibilityLabel и accessibilityRole там, где они необходимы;
- проверка доступности интерактивных компонентов;
- правила не должны ошибочно требовать DOM-атрибуты вроде alt или tabindex.

5. Импорты и архитектура:
- удаление неиспользуемых импортов;
- единый порядок импортов;
- корректная обработка TypeScript path aliases;
- запрет импортов backend-кода во frontend;
- соблюдение существующих границ между screens, components, hooks, services и другими обнаруженными слоями;
- выявление циклических зависимостей, если проверка надёжна и не создаёт существенного замедления.

6. Тесты:
- тестовые globals не должны вызывать ложные ошибки;
- правила тестирования применять только к тестовым файлам;
- проверять корректное использование React Native Testing Library, если она установлена;
- разрешить необходимые послабления для mocks, fixtures и test helpers.

Не устанавливай плагин только из-за его популярности. Если популярный модуль
устарел, не поддерживает текущую версию ESLint или дублирует базовую
конфигурацию Expo, выбери более подходящую альтернативу и зафиксируй причину
в плане.

Не отключай полезные правила глобально ради прохождения существующего кода.
Используй точечные overrides для тестов, конфигурационных файлов, scripts,
mocks и сгенерированного кода.

Требования для backend:

- учитывать фактически используемую версию NestJS;
- контроллеры должны оставаться тонким транспортным слоем;
- бизнес-логика не должна размещаться в контроллерах;
- запретить прямой доступ к инфраструктурным деталям из слоёв, где это нарушает существующую архитектуру;
- учитывать NestJS decorators, dependency injection, DTO, guards, interceptors, filters и modules;
- не создавать ложные ошибки для методов, используемых NestJS через decorators и metadata;
- обеспечить безопасную обработку Promise в контроллерах, сервисах и провайдерах;
- предусмотреть отдельные исключения для migrations, seeds, scripts, тестов и mock-реализаций.

Интеграция с форматированием:

- выяснить, используется ли Prettier;
- ESLint и Prettier не должны содержать конфликтующие правила;
- форматирование и статический анализ должны иметь чётко разделённую ответственность;
- не добавлять Prettier, если проект уже использует другой согласованный механизм форматирования, без обоснования.

Команды:

- должна существовать команда lint для проверки всего проекта;
- должны существовать отдельные команды проверки frontend и backend;
- должна существовать безопасная команда автоматического исправления;
- lint-команды должны завершаться с ненулевым exit code при обнаружении ошибок;
- команды должны быть пригодны для локальной разработки и последующего использования в CI.

Совместимость:

- используй текущий package manager проекта;
- учитывай существующую структуру двух приложений;
- не выполняй неоправданную миграцию конфигурации и не меняй версии основных фреймворков;
- не меняй продуктовое поведение задачи 002-phone-otp-auth;
- существующий код из 002-phone-otp-auth должен проходить lint либо быть аккуратно исправлен без изменения поведения;
- не отключай полезные правила глобально только ради прохождения существующего кода;
- точечные отключения разрешены только с понятным обоснованием;
- не добавляй тяжёлые зависимости без подтверждённой необходимости.

Критерии приёмки:

1. ESLint корректно проверяет frontend и backend.
2. Для каждого приложения применяются правила, соответствующие его стеку.
3. Общие TypeScript-правила не дублируются без необходимости.
4. Код, созданный в 002-phone-otp-auth, проходит проверку.
5. Автоматические исправления не меняют бизнес-поведение.
6. ESLint и форматтер не конфликтуют.
7. Сгенерированные файлы и результаты сборки не проверяются.
8. Ошибочный TypeScript-код приводит к падению lint-команды.
9. Все lint-команды задокументированы.
10. Конфигурация остаётся понятной и расширяемой для следующих фич.

Не реализовывай новые продуктовые функции. Не изменяй OTP, регистрацию, legal-документы, платежи, баланс, MQTT, выдачу воды и реферальную программу.

Если текущая структура проекта, существующие конфигурации или код задачи 002-phone-otp-auth противоречат требованиям, зафиксируй это как уточнение или предположение в спецификации, не скрывая конфликт.
