  ## Цель планирования

  Спроектировать надёжную реализацию простой реферальной программы:

  - один стабильный уникальный промокод на зарегистрированного пользователя;
  - referral deep link;
  - применение кода при регистрации после OTP и legal;
  - явное применение кода зарегистрированным пользователем;
  - блокировка применения после будущей первой успешной покупки;
  - неизменяемая связь inviter/invitee;
  - однократный welcome-бонус новому пользователю;
  - однократный referral-бонус пригласившему;
  - referral summary и история приглашений;
  - минимальная интеграция с React Native приложением.

  Временные development/test значения:

  - welcome-бонус: 10 000 мл;
  - referral-бонус пригласившему: 5 000 мл.

  Приглашённый не получает отдельного referral-бонуса сверх welcome-бонуса.

  Значения должны задаваться backend-конфигурацией и не должны быть зашиты в
  mobile. Существующим пользователям welcome-бонус задним числом не начисляется.

  Не планируй платежи, покупку воды, QR, карту, автоматы, MQTT, dispensing,
  source buckets, bonus-first списание, многоуровневые referrals или
  административное изменение баланса.

  ## Promo Code Strategy

  Выбери и обоснуй конкретную стратегию промокодов:

  - канонический формат;
  - длина;
  - допустимый алфавит;
  - case-insensitive comparison;
  - trim и normalization;
  - защита от визуально неоднозначных символов;
  - источник случайности;
  - достаточная collision resistance;
  - database uniqueness;
  - retry при collision;
  - защита от предсказуемого перебора;
  - максимальная длина входного значения;
  - безопасная публичная ошибка для неизвестного кода.

  Не включай phone number, user ID или другую приватную/предсказуемую информацию
  в публичный promo code.

  Определи канонический referral deep link и его поведение для:

  - signed-out пользователя;
  - незавершённой регистрации;
  - signed-in пользователя без inviter;
  - пользователя с уже применённым кодом;
  - пользователя с закрытой eligibility.

  Учитывай существующий `kaynann://register?promo=...` flow и не ломай его без
  обоснования.

  ## Существующие пользователи

  Выбери один вариант и обоснуй его.

  ## Транзакции, идемпотентность и recovery

  Подробно сравни минимум два варианта:

  1. Одна PostgreSQL-транзакция для relationship, entitlement и wallet credit.
  2. Durable bonus entitlement с идемпотентной доставкой в wallet и recovery
     worker/process.

  Для каждого варианта оцени:

  - совместимость с текущими Prisma и wallet boundaries;
  - влияние на модульные границы;
  - поведение registration completion;
  - retries после caller timeout;
  - concurrent apply;
  - temporary wallet failure;
  - application restart;
  - невозможность потерять обязательное начисление;
  - риск двойного начисления;
  - операционную сложность;
  - необходимость новой очереди или зависимости.

  Выбери один основной подход.

  Предпочитай простое решение на существующем PostgreSQL и текущих NestJS
  возможностях. Не добавляй Redis queue или новую тяжёлую dependency без
  подтверждённой необходимости.

  Основная стратегия должна гарантировать:

  - one welcome entitlement per new user;
  - one relationship per invitee;
  - one inviter entitlement per relationship;
  - stable wallet business key;
  - idempotent registration completion;
  - idempotent repeated apply;
  - deterministic conflicting retry;
  - safe concurrent application одного и разных promo codes;
  - отсутствие lost bonus;
  - отсутствие duplicate wallet credit;
  - восстановление после сбоя между referral state и wallet credit;
  - отсутствие ложного ответа об успешном завершении referral effects;
  - полное сохранение уже завершённой OTP/legal/session логики.

  Определи recovery policy:

  - кто запускает повтор;
  - как выбираются незавершённые entitlements;
  - lease/claim strategy;
  - retry classification;
  - bounded backoff;
  - максимальное количество попыток либо стратегия постоянного восстановления;
  - поведение при permanent conflict;
  - метрики и структурированные логи;
  - безопасный ручной операционный retry без ручного изменения баланса;
  - shutdown и concurrent worker safety.

  Не создавай distributed transaction и не заявляй exactly-once delivery.
  Гарантируй exactly-once wallet effect через durable uniqueness и идемпотентный
  wallet command.

  ## Registration Integration

  Опиши точную последовательность для:

  - регистрации без promo code;
  - регистрации с действительным promo code;
  - регистрации с неизвестным promo code;
  - self-referral;
  - повторного completion с тем же idempotency key;
  - конкурентных completion requests;
  - сбоя после создания user/legal/session, но до wallet credit;
  - повторного запуска после process crash.

  Зафиксируй, где должны быть созданы:

  - promo code нового пользователя;
  - referral eligibility;
  - welcome entitlement;
  - relationship;
  - inviter entitlement.

  Не меняй публичный response регистрации и не добавляй bonus amount в session
  credentials.

  Если полная синхронная обработка бонуса сделает registration ненадёжной,
  обоснуй наблюдаемую eventual-consistency модель. Она всё равно должна
  гарантировать отсутствие потерянных начислений и выполнение принятого в spec
  предела видимости результата.

  ## Post-Registration Apply

  Опиши command flow для зарегистрированного пользователя:

  - canonicalization и validation;
  - session-derived invitee identity;
  - проверка self-referral;
  - проверка существующей relationship;
  - проверка eligibility lock;
  - конкурентное применение одного кода;
  - конкурентное применение разных кодов;
  - idempotent retry;
  - conflicting retry;
  - создание relationship и inviter entitlement;
  - доставка бонуса через wallet;
  - response до и после recovery.

  Определи механизм idempotency публичной apply-команды и необходимость
  `Idempotency-Key`.

  ## Future Purchase Eligibility Contract

  Спроектируй внутренний application contract, который будущая purchase-feature
  сможет вызвать при первой успешно завершённой покупке.

  Контракт должен:

  - принимать стабильную identity успешной покупки;
  - определять пользователя через trusted caller input;
  - закрывать eligibility ровно один раз;
  - быть идемпотентным;
  - не закрывать eligibility для failed, cancelled или incomplete purchase;
  - корректно конкурировать с apply promo;
  - иметь детерминированный результат, если apply и successful purchase происходят
    одновременно;
  - не быть публичным HTTP endpoint;
  - не реализовывать purchase-модель в feature 005.

  Явно выбери правило конкурентного порядка apply и lock. Предпочтительно
  результат должен определяться порядком успешной фиксации в базе, без
  эвристических временных окон.

  ## Фазы внедрения

  Раздели план на небольшие проверяемые фазы, пригодные для последующего
  `$speckit-tasks` и поэтапного `$speckit-implement`.

  Предпочтительная последовательность:

  1. Domain contracts, bonus configuration и promo-code rules.
  2. Prisma migration и existing-user promo provisioning.
  3. Referral repository, concurrency и immutable relationships.
  4. Bonus entitlements, wallet delivery и recovery.
  5. Registration completion integration.
  6. Authenticated referral read/apply API.
  7. Mobile API, MobX store, RxJS flow и deep links.
  8. Minimal referral UI и navigation.
  9. Regression, PostgreSQL acceptance и full validation.

  Если исследование покажет другой безопасный dependency order, измени фазы и
  обоснуй это.

  Для каждой фазы укажи:

  - цель;
  - конкретные файлы;
  - зависимости;
  - минимальную проверку;
  - observable completion criteria;
  - риски, которые закрывает фаза.

  ## Команды проверки

  Определи фактически существующие либо обоснованно добавляемые команды для:

  - Prisma format и validate;
  - reviewed migration validation;
  - Prisma client generation;
  - API lint;
  - mobile lint;
  - workspace lint;
  - format check;
  - API typecheck;
  - mobile typecheck;
  - unit tests;
  - targeted integration tests;
  - real PostgreSQL referral tests;
  - auth regression;
  - wallet regression;
  - OpenAPI source/generated consistency;
  - API build;
  - mobile JS build;
  - full acceptance validation.

  Не придумывай команды, которых нет в package.json, без отдельной задачи на их
  добавление.

  ## Ограничения

  - Не устанавливай зависимости и не изменяй production-код на этапе planning.
  - Не изменяй OTP, legal, SMS, registration request/response и session contracts.
  - Не начисляй welcome-бонус существующим пользователям задним числом.
  - Не добавляй invitee referral-бонус сверх welcome-бонуса.
  - Не реализовывай purchase, payment, QR, map, machine, MQTT или dispensing.
  - Не реализовывай source buckets или bonus-first spending.
  - Не добавляй bonus expiry.
  - Не добавляй денежную конвертацию или вывод.
  - Не добавляй admin endpoints.
  - Не переносись на новый ORM, database или queue без доказанной необходимости.
  - Не добавляй тяжёлые зависимости.
  - Не используй floating-point для воды.
  - Не выполняй автоматическую синхронизацию Prisma schema.
  - Не принимай значения mockup как продуктовые требования.
  - Используй текущий package manager и существующие инструменты проекта.
  - Если spec противоречит текущей архитектуре, Prisma-возможностям или
    существующим auth/wallet транзакциям, явно зафиксируй конфликт, выбранное
    решение и последствия.
