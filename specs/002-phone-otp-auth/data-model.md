# Data Model: Phone OTP Authentication

## Storage Boundary

- PostgreSQL contains durable identity, legal, session, token-lineage, and
  minimal SMS delivery/audit records.
- Redis contains expiring challenges, scoped registration authorization,
  cooldowns, locks, rate counters, and budget reservations.
- Device SecureStore contains only the current refresh credential and, while a
  legal flow is pending, the registration credential.
- Plaintext OTP, refresh credentials, access credentials, registration
  credentials, Orange secrets, and complete provider payloads are never stored
  server-side.

## PostgreSQL

All IDs are UUIDs generated by the application or database. Timestamps are UTC
`timestamptz`. Migrations, not schema synchronization, create all structures.

### User

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | primary key |
| `phoneE164` | varchar(16) | normalized Senegal number, required |
| `phoneConfirmedAt` | timestamptz | required at creation |
| `status` | enum | `ACTIVE`, `SUSPENDED`; feature creates only `ACTIVE` |
| `createdAt` | timestamptz | required |
| `updatedAt` | timestamptz | required |

Indexes and constraints:

- unique `phoneE164`; deletion/account reuse is outside this feature;
- check `phoneE164 LIKE '+221%'`;
- index `(status, id)` for authorization lookup.

Lifecycle: no User exists for an OTP-only participant. It is created in the same
transaction as mandatory legal acceptances and the initial session.

| `createdAt` | timestamptz | required |

Indexes and constraints:

- unique `(kind, version, locale)`;
- raw migration partial unique index `(kind, locale) WHERE is_current = true`;
- index `(mandatory, isCurrent, locale)`.

Lifecycle: publish a new immutable row and switch `isCurrent` in one transaction.
Never edit accepted content in place.

### UserSession

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | primary key and JWT `sid` |
| `userId` | UUID | FK User |
| `familyId` | UUID | rotation family |
| `installationFingerprint` | char(64) | required |
| `creationKeyDigest` | char(64) | unique, supports registration idempotency |
| `status` | enum | `ACTIVE`, `REVOKED`, `EXPIRED` |
| `expiresAt` | timestamptz | immutable `createdAt + 60 days` absolute deadline |
| `lastUsedAt` | timestamptz | nullable |
| `revokedAt` | timestamptz | nullable |
| `revokeReason` | enum | nullable: `LOGOUT`, `REPLAY`, `ADMIN`, `EXPIRED` |
| `replayDetectedAt` | timestamptz | nullable |
| `createdAt` | timestamptz | required |
| `updatedAt` | timestamptz | required |

Indexes and constraints:

- unique `familyId`, unique `creationKeyDigest`;
- index `(userId, status)`;
- index `(expiresAt, status)` for cleanup;
- `expiresAt` is assigned once when the session is created and is never changed
  by refresh rotation, activity, restart, legal acceptance, or idempotent
  registration recovery;
- no unique installation constraint: a device may deliberately start a new
  session while older sessions remain revocable.

### SessionRefreshToken

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | primary key |
| `sessionId` | UUID | FK UserSession |
| `tokenDigest` | char(64) | unique HMAC digest |
| `generation` | integer | starts at 0, strictly increasing |
| `status` | enum | `ACTIVE`, `ROTATED`, `REVOKED`, `EXPIRED` |
| `issuedAt` | timestamptz | required |
| `usedAt` | timestamptz | nullable |
| `expiresAt` | timestamptz | required; equals parent `UserSession.expiresAt` |
| `replacedById` | UUID | nullable self-FK |

Indexes and constraints:

- unique `(sessionId, generation)`;
- partial unique index on `sessionId WHERE status = 'ACTIVE'`;
- index `(tokenDigest)` and `(expiresAt, status)`.

Rotation transaction conditionally updates the presented ACTIVE row. A zero-row
claim followed by finding ROTATED means replay and revokes every row in the
session family. Repository logic enforces the cross-table invariant that every
generation inherits the unchanged session deadline. Token history is retained
with the session for 90 days after its absolute expiry or revocation, then
deleted by a scheduled cleanup.

| Field | Type | Rules |

| `provider` | enum | `FAKE`, `ORANGE` |
| `providerMessageId` | varchar(255) | nullable until accepted |
| `phoneFingerprint` | char(64) | keyed fingerprint, not phone |
| `status` | enum | `PREPARED`, `ACCEPTED`, `DELIVERED`, `UNCERTAIN`, `FAILED` |
| `failureCategory` | enum | nullable normalized category |
| `requestedAt` | timestamptz | required |
| `acceptedAt` | timestamptz | nullable |
| `lastReceiptAt` | timestamptz | nullable |
| `deliveredAt` | timestamptz | nullable |
| `updatedAt` | timestamptz | required |

Indexes and constraints:

- unique `(provider, providerMessageId)` when message ID is not null;
- unique `challengeId`;
- index `(status, updatedAt)` for receipt metrics/cleanup.

Retention: 30 days for routine delivery records, with aggregate metrics retained
separately. No SMS body, OTP, complete recipient, OAuth data, or callback
payload. Repeated receipt status is an idempotent no-op; legal forward
transitions update timestamps; unknown IDs are counted and acknowledged.

## Redis

Phone, IP, and installation key segments use HMAC fingerprints. `challengeId`
and `registrationFlowId` are random UUIDs. TTL is set atomically with values.

### OTP challenge

Keys:

```text
otp:challenge:{challengeId}
otp:current:{phoneFingerprint}
otp:tombstone:{challengeId}
otp:send-lock:{phoneFingerprint}
otp:cooldown:{phoneFingerprint}
```

Challenge fields:

| Field | Meaning |
|---|---|
| `challengeId` | public opaque correlation ID |
| `phoneFingerprint` | keyed lookup identity |
| `phoneE164` | recipient used only inside protected transient state |
| `otpDigest` | HMAC-SHA-256 |
| `hmacKeyVersion` | secret rotation selector |
| `attemptsRemaining` | starts at 5 |
| `state` | `PREPARED`, `ACTIVE` |
| `createdAt` | server code-generation timestamp |
| `activatedAt` | nullable provider-accepted/uncertain activation timestamp |
| `expiresAt` | immutable `createdAt + 5 minutes` |
| `provider`, `providerMessageId` | normalized technical metadata |
| `pendingPromoCode` | optional opaque bounded context |

TTL and deletion:

- PREPARED: up to 30 seconds and never beyond `expiresAt`;
- ACTIVE: only the remaining interval until the immutable `expiresAt`; provider
  latency and activation never restart or extend the five-minute lifetime;
- send lock: 15 seconds, owner-token release only;
- cooldown: 60 seconds from accepted/uncertain send;
- USED tombstone: 10 minutes, no digest/phone;
- EXHAUSTED tombstone and phone failure event: 30 minutes / 24 hours.

State transitions:

```text
none -> PREPARED -> ACTIVE -> USED
                  -> EXHAUSTED
PREPARED -> deleted on definitive send failure
ACTIVE -> replaced by newer accepted/uncertain ACTIVE
ACTIVE -> expired by TTL
```

Concurrency:

- send lock prevents simultaneous candidate creation per phone;
- activation script rejects an expired candidate, preserves its absolute
  `expiresAt`, applies only the remaining Redis TTL, and swaps `otp:current` and
  candidate atomically;
- verify reads the digest for timing-safe comparison, then a Lua CAS validates
  current ID/state/version and consumes or decrements exactly once;
- two correct requests cannot both transition ACTIVE to USED.

### Registration authorization

Key: `auth:registration:{tokenDigest}`.

Fields: `registrationFlowId`, `state` (`ACTIVE`, `COMPLETING`, `COMPLETED`),
`phoneE164`, `phoneConfirmedAt`, optional `existingUserId`, required current
legal document IDs observed at issuance, pending promo context,
`installationFingerprint`, `completionKeyDigest`, deterministic `sessionId`, and
safe completion metadata. Completion metadata includes an AES-256-GCM
`completionResultCiphertext`, random 96-bit `completionResultNonce`,
`completionResultKeyVersion`, and authentication tag. AAD binds the envelope to
`registrationFlowId`, `completionKeyDigest`, and `sessionId`; no plaintext token
is stored.

TTL: 15 minutes total, never extended by reads or failed writes. A short
owner-token lease serializes completion. On success, remove phone and promo
fields, mark COMPLETED, retain the same original expiry, and permit only a
same-idempotency-key recovery of the exact sealed credential result for the same
session. Recovery never creates a refresh generation or advances lineage.

### Rate, block, and budget keys

```text
abuse:phone-hour:{window}:{phoneFingerprint}
abuse:phone-day:{window}:{phoneFingerprint}
abuse:ip-hour:{window}:{ipFingerprint}
abuse:install-hour:{window}:{installationFingerprint}
abuse:install-day:{window}:{installationFingerprint}
abuse:exhausted:{phoneFingerprint}
abuse:block:{phoneFingerprint}
sms:global-day:{window}
sms:cost-day:{window}
sms:global-semaphore
sms:provider-second:{window}
```

Window counters are fixed-window MVP controls with atomic limit checks and
reservation. Hour counters expire at window end plus one hour; day counters at
48 hours. Exhaustion history expires after 24 hours, block after 30 minutes,
semaphore leases after the provider timeout ceiling, and second-window
throughput counters after two seconds.

Definitive no-send failures refund global count/cost reservation but do not
refund per-actor attempts, preventing free provider probing. Accepted and
uncertain sends retain every reservation.

## Transaction Boundaries

### New registration

Before opening the Prisma transaction, generate the deterministic bootstrap
credentials and write their AES-256-GCM sealed response envelope to the
registration authorization in Redis. The envelope remains inaccessible to the
client while the authorization is `COMPLETING`.

Then run one Prisma transaction:

1. re-read and lock/consistently query current mandatory legal documents;
2. reject if submitted IDs differ;
3. insert User by unique phone or resolve the concurrent winner;
4. insert acceptances with unique conflict protection;
5. create/get deterministic UserSession by `creationKeyDigest`;
6. insert the generation-zero ACTIVE refresh digest from the prepared envelope.

No session credential is returned before commit. Redis registration state is
marked completed only after PostgreSQL succeeds. A same-key recovery opens the
existing envelope only after confirming COMPLETED state and returns the same
credential bytes without refresh rotation; a different key is rejected. If a
process failure occurs after commit but before the Redis transition, recovery
confirms that the deterministic session and generation-zero digest match the
prepared envelope and atomically repairs the Redis state. Without a matching
durable aggregate, retry reuses the same envelope in a new Prisma transaction.
Redis and PostgreSQL are not treated as one distributed transaction.

### Existing user with stale legal

One transaction rechecks current legal IDs, inserts missing exact acceptances,
creates one deterministic device session, and creates its initial refresh row.

### Refresh rotation

One transaction uses the PostgreSQL clock to conditionally claim ACTIVE token
status only when `UserSession.expiresAt` is still in the future, inserts the next
generation with that same deadline, links `replacedById`, and updates session
activity. A final database-side deadline predicate prevents a concurrent request
from extending or renewing an expired session. At or after the deadline, the
transaction marks the session and current token `EXPIRED` and returns no
credential. A known non-ACTIVE digest triggers family/session revocation in the
same transaction.

Issued access JWT expiry is `min(issuedAt + 15 minutes,
UserSession.expiresAt)`. The access guard also rejects a non-ACTIVE or expired
session. Only a later successful OTP authentication may create a separate
session with a new 60-day absolute window.

## Data Protection

- Separate versioned HMAC keys for OTP, credentials, phone/IP/install
  fingerprints, and idempotency derivation.
- E.164 is stored only where required for identity/delivery; operational
  correlation uses fingerprints.
- Never put phone, legal content, promo code, or bearer credentials in JWT.
- PostgreSQL backups and Redis transport/authentication follow deployment
  security policy; HTTPS is mandatory at the public boundary.
