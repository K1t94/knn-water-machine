# Research: Phone OTP Authentication

**Date**: 2026-07-29

## Confirmed By The Existing Project

### Existing runtime and repository shape

**Decision**: extend `apps/api` and `apps/mobile` in the pnpm monorepo.

**Rationale**: bootstrap already fixes NestJS 11, Expo SDK 54 with a development
client, Prisma/PostgreSQL, node-redis/Redis, Zod/class-validator, Vitest,
Supertest, Docker Compose, environment validation, redacted exceptions, and
root validation scripts. Creating another project or package would duplicate
bootstrap.

**Alternatives considered**: a standalone auth service and a shared contracts
package. Both are premature for one consumer and conflict with bootstrap scope.

### Persistence

**Decision**: Prisma migrations own PostgreSQL changes; a shared API-local Redis
module owns transient state.

**Rationale**: the repository already uses Prisma 6 and PostgreSQL 17 and has a
Redis 7 service and client dependency. Durable security/audit state needs
PostgreSQL; expiring challenges and counters need Redis.

**Alternatives considered**: OTP in PostgreSQL, in-process caches, or a new
transient store. They respectively increase contention, fail across API
instances, or duplicate infrastructure.

### Validation and public contracts

**Decision**: keep global class-validator boundary validation, extend Zod
environment validation, and add Nest Swagger/OpenAPI generation.

**Rationale**: bootstrap has a strict global `ValidationPipe` and safe exception
filter but no auth DTOs or OpenAPI dependency. MVP v0.12 requires Swagger.

**Alternatives considered**: handwritten-only docs or returning framework
exceptions. Neither provides a verifiable client contract.

### Observability export

**Decision**: add a feature-local `prom-client` registry behind an
`ObservabilityModule` and expose it through configurable
`GET /internal/metrics`. `INTERNAL_METRICS_ENABLED=false` removes the route;
when enabled it requires an independent bearer credential from
`INTERNAL_METRICS_TOKEN`, compared in constant time. The secret must contain at
least 32 bytes generated by a cryptographically secure random source, use
base64url encoding so decoded length is configuration-testable, and never be
logged. Staging and production fail startup if exposition is enabled without a
valid token. The endpoint remains outside public OpenAPI. Export current SMS
count/XOF utilization and warning/critical threshold series; deployment-owned
monitoring defines the actual alert rules.

**Rationale**: bootstrap provides health checks and safe logging but no metrics
registry, exporter, alerting platform, or established private network boundary.
A dedicated registry gives FR-048 and FR-049 a contract-testable operational
output without creating a workspace package or coupling auth services to a
specific deployment monitoring stack. Application authorization therefore
cannot depend on assumed ingress behavior or trusted proxy headers. The
deployment must additionally restrict the endpoint to monitoring sources at
ingress, firewall, or service-network level as defense in depth, but that new
deployment requirement does not replace the bearer check. Keeping alert
evaluation outside the application avoids inventing unavailable infrastructure
while still exposing deterministic alert inputs.

**Alternatives considered**: in-memory counters without exposition, adding a
full OpenTelemetry stack, application-owned notification alerts, relying only
on a network allowlist, using client IP/proxy headers as authorization, a
separate metrics port, and mTLS. In-memory counters do not satisfy operational
access, while a full telemetry stack and application-owned alerts exceed the
current scope. A network allowlist alone is deployment-specific and leaves
local/misconfigured exposure unprotected; proxy headers are not credentials.
A separate port still requires network controls, and mTLS is preferable only
after the deployment platform provides certificate lifecycle management.
Bearer authorization plus a deployment allowlist is the smallest verifiable
defense-in-depth design supported by the current repository.

### SMS budget alert thresholds

**Decision**: expose independently configurable warning and critical
percentages for daily SMS count and daily XOF spend. Defaults are 80% warning
and 95% critical for both dimensions. With the planned hard limits this yields
400/475 SMS and 8,000/9,500 XOF. Validate integer percentages with
`0 < warning < critical < 100`, calculate absolute threshold gauges with
`ceil(limit * percent / 100)`, and evaluate them against authoritative Redis
daily counters using the same UTC window. Thresholds are observability inputs;
only the 100% count or spend budget is an application-enforced hard stop.

**Rationale**: 80% leaves meaningful time for operations to investigate usage
or replenish/configure the Orange bundle, while 95% identifies imminent
exhaustion without conflating an alert with the hard budget guard. Independent
count and XOF percentages allow later tuning when the customer confirms bundle
pricing. Percentage-based configuration remains coherent when either hard
limit changes, and deterministic absolute gauges keep deployment alert rules
simple.

**Alternatives considered**: no defaults, absolute threshold configuration,
one shared percentage pair, and application-owned notifications. No defaults
leave FR-048 operational output incomplete in a deployable configuration.
Absolute values can silently drift when hard limits change. A shared pair
prevents count and cost from being tuned independently. Notification delivery
requires deployment infrastructure that bootstrap does not provide.

## Feature Decisions

### Phone normalization

**Decision**: use `libphonenumber-js` on API and mobile, parse with default
region `SN`, require a valid result whose country is `SN` and country calling
code is `221`, and store/send E.164. Server validation is authoritative.

**Rationale**: maintained numbering metadata is safer than hard-coded prefix
rules and supports local input. Google explicitly warns that prefix-based
carrier data indicates original allocation, not current carrier after
portability ([libphonenumber](https://github.com/google/libphonenumber)).

**Alternatives considered**: regex-only validation or carrier-prefix routing.
Regex becomes stale; carrier inference is explicitly prohibited.

### Redis atomicity

**Decision**: versioned Lua scripts loaded and invoked by SHA.

**Rationale**: Redis executes scripts atomically, allowing challenge, attempt,
cooldown, lock, rate, and budget transitions to be checked together
([Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)).
`WATCH/MULTI` would require retry loops across more keys and is easier to misuse.

**Alternatives considered**: `WATCH/MULTI`, Redlock, and database row locks.
Lua is the smallest mechanism compatible with the existing single Redis
dependency. Deployment must keep these keys in one atomic Redis deployment.

### OTP protected representation

**Decision**: generate with Node `crypto.randomInt`, HMAC with a versioned
server secret and challenge/phone context, compare fixed-size bytes using
`crypto.timingSafeEqual`, then atomically consume by challenge version in Lua.

**Rationale**: a raw hash of a six-digit value is brute-forceable. HMAC prevents
offline guessing if Redis is exposed, and the final Lua compare-and-consume
prevents concurrent success.

**Alternatives considered**: plaintext, unsalted SHA-256, bcrypt, or encrypted
OTP. Plaintext/encryption expands disclosure risk; SHA-256 is weak for a tiny
space; bcrypt adds cost without solving atomicity.

### Registration authorization

**Decision**: use a 15-minute opaque 256-bit bearer credential with HMAC lookup
state in Redis, scoped to legal read/context update/completion. Before the
PostgreSQL commit, seal the prepared completion response with AES-256-GCM using
a versioned server key, random 96-bit nonce, and AAD containing the registration
flow, idempotency-key digest, and deterministic session ID. Redis stores only
the sealed envelope; PostgreSQL stores only the bootstrap refresh digest.
Same-key retries return that exact envelope result and never rotate refresh
lineage.

**Rationale**: stateful authorization supports revocation, one-time transition,
idempotent response recovery, and pending context without granting application
access. Preparing the sealed result before the database transaction permits
recovery after a commit/response boundary failure without storing plaintext
credentials or manufacturing a second refresh generation.

**Alternatives considered**: JWT registration token or immediately creating a
pending User, rotating the bootstrap refresh credential on each retry, or
storing a plaintext response cache. JWT is harder to revoke and coordinate; a
pending User contradicts the requirement that OTP challenges are not users and
user creation waits for legal acceptance. Retry rotation can make out-of-order
responses stale and trigger replay revocation; plaintext response caching is
prohibited.

### Pending promo code

**Decision**: carry at most 64 safe printable characters from mobile to OTP
state and then registration state; allow replace/delete; discard on completion.

**Rationale**: this preserves future context without importing or designing a
ReferralModule. The code does not influence any decision or database write.

**Alternatives considered**: User columns, referral tables, or validation
calls. All would implement deferred referral behavior.

### Access and refresh credentials

**Decision**: signed HS256 access JWT for at most 15 minutes plus an opaque
random refresh credential within an absolute 60-day `UserSession` window. The
window is fixed at session creation; every refresh generation has the same
deadline and rotation never extends it. Access expiry is capped at the session
deadline. Store only keyed digests and rotation history. Every access request
checks active session state and its absolute expiry.

**Rationale**: the API is currently a single NestJS trust boundary, so HS256
avoids unjustified key-distribution complexity. Nest supports JWT bearer flows
through `@nestjs/jwt` ([NestJS authentication](https://docs.nestjs.com/security/authentication)).
Opaque refresh values make rotation/replay state explicit. An absolute window
bounds the useful lifetime of a stolen credential even when the legitimate
client remains active. Rotation protects against replay; it does not convert
the session into an indefinitely renewable login.

**Alternatives considered**: a sliding 60-day refresh lifetime, refresh JWTs,
plaintext refresh rows, or RS256. A sliding lifetime permits an indefinitely
renewable session and increases exposure after credential compromise. Refresh
JWTs do not remove server lineage needs; plaintext is prohibited; RS256 is
useful only when independent verifiers exist.

### Mobile secure storage and navigation

**Decision**: install Expo SDK-compatible `expo-secure-store` using
`npx expo install`; store refresh and registration credentials with
device-only/unlocked accessibility, keep access in memory, and use a minimal
React Navigation native stack. Install `@react-navigation/native`,
`@react-navigation/native-stack`, `react-native-screens`, and
`react-native-safe-area-context`, resolving the two native peer packages through
`npx expo install`. Use development-only `@testing-library/react-native` with
the existing Vitest runner; do not add deprecated `react-test-renderer` or a
second Jest-based test stack. Extend the existing Vitest include patterns so
both colocated `src/**/*.spec.{ts,tsx}` state tests and
`__tests__/**/*.test.tsx` component-flow tests are collected. Add a shared
`apps/mobile/vitest.setup.ts` registered through `setupFiles` to install the
React Native Testing Library matchers and deterministic mocks for Expo
SecureStore, React Native Safe Area Context, React Navigation/native-stack, and
other native-only modules used by the authentication flow. Prove the harness
before feature component tests with a minimal
`apps/mobile/__tests__/test-harness.test.tsx` render and interaction smoke test.

**Rationale**: SecureStore encrypts Android values with Keystore and uses iOS
Keychain and is compatible with Expo config plugins
([Expo SDK 54 SecureStore](https://docs.expo.dev/versions/v54.0.0/sdk/securestore/)).
AsyncStorage is not suitable for bearer secrets. Native-stack is additive to
the current single `App.tsx` and does not require file-based routing migration.
React Navigation documents `react-native-screens` and
`react-native-safe-area-context` as the native dependencies and recommends
Expo-aware installation
([React Navigation setup](https://reactnavigation.org/docs/getting-started/)).
Expo recommends `@testing-library/react-native` for React Native component tests
and explicitly deprecates `react-test-renderer` for React 19+
([Expo unit testing](https://docs.expo.dev/develop/unit-testing/)).

**Alternatives considered**: AsyncStorage, `react-native-keychain`, and Expo
Router. AsyncStorage is insecure; keychain adds a less Expo-native dependency;
Router would restructure the bootstrap application. Jest with `jest-expo` would
duplicate the Vitest infrastructure selected in bootstrap.

### Mobile reactive state and asynchronous orchestration

**Decision**: add `mobx`, `mobx-react-lite`, and `rxjs`. MobX is the sole owner
of observable application state. `SessionStore` alone owns access, session, and
root-route state; `OtpStore` owns phone/OTP/challenge/UI state; and
`RegistrationStore` owns registration/legal/pending-promo UI state. No
observable `AuthStore` duplicates those values. The non-observable composition
root owns only the application-root `SessionStore` and `SessionFlowService`. It
may expose child-scope factories, but must not retain created `OtpStore`,
`OtpFlowService`, `RegistrationStore`, or `RegistrationFlowService` instances
after handing ownership to their providers, and it may not mirror application
state. Stores use observable fields, computed values, and actions.
`apps/mobile/src/mobx.config.ts` enables `enforceActions: "always"` and is
imported by the mobile bootstrap before any store is constructed. Functional
React Native screens that read store state use `observer`. RxJS is restricted
to application services that coordinate asynchronous flows requiring
cancellation, concurrency policy, server-time timers, retry policy, or
composition of event sources.

The typed `fetch` client and SecureStore wrappers remain Promise-based adapters
without React or RxJS ownership. The command path is
`Screen -> typed FlowService command -> Promise adapter -> store action`; the
render path is `MobX store -> observer screen`. A typed composition context
provides `{ store, commands }` references. Screens do not call APIs,
SecureStore, internal store-transition actions, or RxJS subjects. Reactive
services adapt Promise calls with `defer`/`from`, update MobX only through store
actions, keep subjects and subscriptions private, and expose an idempotent
`dispose()`. `exhaustMap` suppresses duplicate submissions while a request is
active; a resettable shared stream provides refresh single-flight;
deterministic timers derive countdown updates from server timestamps. RxJS
never automatically retries OTP sends or another side-effecting mutation unless
the API operation is idempotent and retains the same idempotency key.

Service ownership is explicit. `OtpFlowService` lives for the phone/OTP
authentication flow and is disposed when its provider unmounts or the flow is
replaced. `RegistrationFlowService` lives for the registration/legal flow and
is disposed on completion, cancellation, or replacement. `SessionFlowService`
lives for the application root and is disposed only when that root unmounts.
Child providers unregister and release their instances on disposal, and tests
prove the composition root retains no disposed child reference. Tests exercise
each boundary independently.

**Rationale**: this separation provides one inspectable source of current UI
state while using RxJS only where stream semantics add value. MobX documents
that `observer` subscribes functional components to observables read during
render and recommends the lightweight `mobx-react-lite` binding
([MobX React integration](https://mobx.js.org/react-integration.html)). RxJS
defines subscriptions as disposable resources and `exhaustMap` as ignoring new
inner work while prior work remains active
([RxJS subscriptions](https://rxjs.dev/guide/subscription),
[RxJS exhaustMap](https://rxjs.dev/api/operators/exhaustMap)). Explicit
ownership and disposal prevent timers or network workflows from surviving their
application scope.

**Alternatives considered**: React reducers/context, MobX without RxJS, RxJS
`BehaviorSubject` state stores, Redux Toolkit, Zustand, and XState. Reducers were
the previous feature-local plan but conflict with the approved project-wide
reactive architecture. MobX alone makes complex cancellation and concurrency
policies less explicit. RxJS state subjects would duplicate MobX and create two
sources of truth. The other state frameworks add a third state model without a
feature requirement.

### Retention scheduling

**Decision**: add `@nestjs/schedule`, initialize `ScheduleModule.forRoot()` once
in the API root module, register the scheduler and retention service as
`AuthModule` providers, and run retention daily at `03:00 UTC`. Configure the
cron handler with `waitForCompletion: true`. The retention service starts one
Prisma interactive transaction and attempts `pg_try_advisory_xact_lock`; it
skips cleanup if the lock is unavailable and otherwise performs all deletion in
the same transaction. Keep deletion logic idempotent and callable directly by
tests. Unit tests cover cron/provider wiring and same-process overlap. A Docker
PostgreSQL integration test uses two independent Prisma connections to prove
that only the successful transaction-scoped lock holder deletes rows, the
losing transaction performs no deletion, and the lock is available again after
the winning transaction ends. Redis OTP tombstones, rate-limit counters, and
budget keys remain TTL-managed and are tested with the Redis state machine and
anti-abuse suites; the PostgreSQL retention job never deletes Redis keys.

**Rationale**: Nest's scheduling module provides lifecycle-managed declarative
cron jobs and supports overlap prevention
([NestJS task scheduling](https://docs.nestjs.com/techniques/task-scheduling)).
The process-local guard alone cannot coordinate multiple API replicas, while
PostgreSQL is already required by retention cleanup. A transaction-scoped lock
avoids adding another scheduler service and cannot remain attached to a pooled
connection after the cleanup transaction ends.

**Alternatives considered**: an external deployment cron job, Redis leader
election, and an unmanaged timer. An external job introduces an undeclared
deployment artifact, Redis election adds failure-state complexity, and a raw
timer bypasses Nest lifecycle management.

### OTP autofill

**Decision**: one accessible controlled input rendered as six cells, using
Android `autoComplete="sms-otp"` and iOS `textContentType="oneTimeCode"`.

**Rationale**: React Native exposes platform autofill hints for SMS codes
([React Native TextInput](https://reactnative.dev/docs/textinput)).

**Alternatives considered**: six independent inputs. They make paste, focus,
screen-reader behavior, and OS autofill less reliable.

## Official Orange SMS Senegal Contract

### Product scope

**Finding**: Orange states that the Senegal API sends to Senegal numbers on any
operator; sender names and optional delivery receipts are supported
([Orange SMS Senegal overview](https://developer.orange.com/apis/sms-sn/)).
Orange remains delivery-only in this architecture.

### OAuth

**Decision**: request client-credentials tokens from
`POST https://api.orange.com/oauth/v3/token`, using HTTP Basic authorization
derived from client ID/secret, form content type, and
`grant_type=client_credentials`. Cache the bearer token for `expires_in`
(documented example: 3600 seconds) minus configurable safety skew.

Use a process-local single-flight promise so concurrent sends share one refresh.
On invalid/expired credentials, invalidate once and retry token acquisition only
where safe; never request a token for every SMS.

**Source**: [Orange SMS getting started](https://developer.orange.com/apis/sms/getting-started).

### Send request

**Decision**: call
`POST https://api.orange.com/smsmessaging/v1/outbound/{urlEncodedSenderAddress}/requests`.
For Senegal the sender address format is `tel:+2210000` and must be URL-encoded;
recipient addresses use `tel:+221...`.

The private Orange DTO is:

```json
{
  "outboundSMSMessageRequest": {
    "address": "tel:+221XXXXXXXXX",
    "senderAddress": "tel:+2210000",
    "senderName": "KAYNANN",
    "outboundSMSTextMessage": {
      "message": "KAYNANN code: 123456. Valid for 5 minutes."
    }
  }
}
```

Do not expose this DTO outside the adapter. A `201` response includes a
`resourceURL`; retain the extracted resource identifier as provider message ID.
The production template is GSM-7, link-free, and one segment.

**Source**: [Orange SMS getting started](https://developer.orange.com/apis/sms/getting-started)
and [Senegal API reference](https://developer.orange.com/apis/sms-sn/api-reference).

### Sender Name, balance, and throughput

**Finding**: Sender Name is locally approved/whitelisted and documented as at
most 11 alphanumeric characters/spaces without special characters. The account
needs a positive non-expired contract balance. Senegal documents a 5 SMS/s
limit. `KAYNANN` is syntactically suitable but approval is not assumed.

**Decision**: validate static shape at startup, cap concurrency and throughput,
and map actual approval/balance responses only from documented/mock fixtures.
Bundle pricing is deployment configuration, not code
([Orange Senegal pricing](https://developer.orange.com/apis/sms-sn/pricing)).

### Errors and retry

**Finding**: Orange documents structured request errors and OAuth categories,
including missing/invalid/expired credentials. Exact balance and sender
rejection payloads can depend on the active contract.

**Decision**:

| Category | Retry |
|---|---|
| timeout, network reset, 500/502/503/504 | at most 2 retries, jittered 250 ms then 750 ms |
| Orange 429 | honor bounded `Retry-After`, otherwise one bounded retry |
| invalid recipient/message/request | none |
| invalid credentials/configuration/sender | none after one token refresh where expiration is plausible |
| insufficient balance | none |

Never invent numeric Orange codes. Unknown 4xx is permanent; unknown 5xx is
temporary. Preserve details only in redacted adapter diagnostics.

### Delivery Receipt

**Finding**: Orange can POST a receipt within 24 hours. The documented body
contains `deliveryInfoNotification.callbackData`, address, and delivery status.
Statuses include `DeliveredToNetwork`, `DeliveryUncertain`,
`DeliveryImpossible`, `MessageWaiting`, and `DeliveredToTerminal`. The endpoint
must be public HTTPS on port 443 and answer 200. No cryptographic callback
signature is documented in the public contract.

**Decision**: implement schema parsing and idempotent storage behind a disabled
feature flag. Do not use a receipt as proof of phone ownership or OTP success.
Confirm callback authentication/network allowlisting after credentials.

**Source**: [Orange SMS getting started](https://developer.orange.com/apis/sms/getting-started).

## Post-Credential Questions

These do not block local implementation and cannot be answered safely without
the customer's Orange contract:

1. Are client credentials active for Senegal and what are contract expiry and
   balance responses?
2. Is `KAYNANN` approved as Sender Name, and which sender address is assigned?
3. Does the purchased bundle keep the documented 5 SMS/s quota?
4. Which exact response represents insufficient balance and sender rejection?
5. Is Delivery Receipt enabled, and does Orange provide source ranges,
   signatures, mutual TLS, or another callback-authentication mechanism?
6. Does Senegal network delivery preserve the exact GSM-7 template and produce
   useful receipt timing/statuses across operators?

No live request is allowed until explicit non-production or production
credentials and customer approval are provided.

- MVP v0.12 leaves provider selection open; the current feature clarifies it as
  Orange behind a provider port.
